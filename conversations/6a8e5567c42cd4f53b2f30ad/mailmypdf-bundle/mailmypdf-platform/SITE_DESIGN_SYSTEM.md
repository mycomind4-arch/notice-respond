# MailMyPDF Vertical Site Design System

## Purpose

Create a family of premium, specialized products that share the MailMyPDF foundation without looking like cloned SaaS templates.

## Product hierarchy

MailMyPDF is the fulfillment/platform layer. Vertical products own the domain problem and intelligence.

- Appeal Mail — understand adverse decisions, build evidence-backed appeals, mail and prove delivery.
- Notice Respond — understand official notices, prepare grounded responses, mail and preserve proof.
- Dispute Mail — identify disputes, prepare correspondence, mail and prove timely submission.
- Immigration Mail — organize immigration correspondence, prepare document-grounded responses, mail and preserve proof.
- MailMyPDF Small Business — business correspondence and document mailing workflows.

## Shared visual language

Use the existing Notice Respond implementation as the quality benchmark. Reuse its typography, spacing discipline, border treatment, restrained cards, document-inspired visual language, accessible controls, and responsive behavior where those patterns already exist.

Shared traits:

- editorial serif display typography paired with restrained sans/mono utility text
- warm document/paper surfaces rather than generic SaaS gradients
- thin rules and subtle borders
- rounded but not overly-pill-shaped controls
- strong hierarchy and generous whitespace
- real workflow language instead of generic AI terminology
- visible provenance, review, and trust states
- mobile-first responsive behavior
- accessible contrast, focus states, labels, and keyboard navigation

## Vertical differentiation

Each site gets a distinct accent treatment and domain vocabulary while retaining the same structural grammar.

### Appeal Mail

Tone: serious, protective, analytical, evidence-first.

Visual cues: paper, red/stamp accent, evidence markers, timeline motifs, document review.

Primary message: "Understand the decision. Build the appeal. Mail it with proof."

Primary flow:

Understand → Analyze → Issues → Evidence → Strategy → Draft → Review → Mail → Track → Prove

### Notice Respond

Tone: calm, procedural, authoritative.

Visual cues: official notice/document language, restrained stamp/postmark treatment, clear workflow directory.

Primary flow:

Upload → Identify → Understand → Respond → Review → Mail → Track → Prove

### Dispute Mail

Tone: assertive, practical, consumer-protective.

Visual cues: dispute/error markers, evidence cards, deadlines, correspondence history.

Primary flow:

Identify Error → Gather Evidence → Draft → Review → Mail → Track → Prove

### Immigration Mail

Tone: careful, organized, reassuring without promising outcomes.

Visual cues: case packets, document checklists, chronology, correspondence records.

Primary flow:

Understand Request → Organize Documents → Identify Gaps → Prepare Response → Review → Mail → Track → Prove

### Small Business

Tone: professional, efficient, operational.

Visual cues: business correspondence, saved recipients, reusable templates, mailing history.

Primary flow:

Prepare → Review → Address → Mail → Track → Reuse

## Homepage architecture

Every vertical homepage should answer five questions above the fold:

1. What is this?
2. Who is it for?
3. What can I do with it?
4. What happens after I upload a document?
5. How does MailMyPDF fit in?

Recommended structure:

1. Header
2. Hero with one dominant CTA and one discovery CTA
3. Visible workflow strip
4. Trust/provenance bar
5. Workflow directory preview
6. Product capability section
7. Concrete workflow/process visualization
8. Review/safety section
9. MailMyPDF fulfillment bridge
10. FAQ
11. Footer with ecosystem navigation

## Workflow page architecture

Every real workflow page should feel like a product page, not a blog article.

Required sections:

- workflow identity and category
- problem statement
- who it is for
- documents to upload
- what the system analyzes
- findings/evidence model
- resulting document/response
- review and safety controls
- next action
- MailMyPDF handoff
- related workflows

Catalog-only workflows may have the same polished page structure, but must never imply that an executable intelligence engine exists when it does not.

## Application UX

The application should visually communicate progress through the actual case state rather than a generic chatbot.

Preferred persistent workflow stages:

Document → Understanding → Analysis → Evidence → Draft → Review → Mail → Proof

Use clear states:

- Ready
- Processing
- Needs review
- Warning
- Blocked
- Complete

Never show fake progress or fabricated results.

## MailMyPDF bridge

MailMyPDF should be a meaningful part of the customer journey, not merely a footer logo.

Use language such as:

"Ready to send? Mail this document with MailMyPDF."

Then explain:

- printing
- envelope preparation
- USPS delivery
- tracking
- certified options where supported
- proof/receipt record

The vertical owns preparation and intelligence. MailMyPDF owns physical fulfillment.

## What not to do

- Do not create generic AI SaaS dashboards.
- Do not use giant gradient blobs as the primary visual identity.
- Do not make every vertical a copy with a changed accent color.
- Do not use "Coming Soon" for the public catalog.
- Do not imply catalog workflows are executable when they are not.
- Do not claim mailing, tracking, analysis, or integrations occurred unless the underlying capability actually succeeded.
- Do not replace working domain intelligence merely to make UI components look uniform.

## Quality gate

A vertical is visually ready when:

- homepage feels like a finished product
- workflow discovery is obvious
- primary CTA is unambiguous
- application journey is understandable without explanation
- document/evidence/review states are polished
- mobile layout is intentional
- accessibility is respected
- MailMyPDF handoff is natural
- catalog and executable runtime are clearly separated
- no placeholder or fake-result UI remains
